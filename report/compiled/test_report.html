[[LOC:ABSTRACT]]
Abstract

Finding safe, affordable rental accommodation near university campuses in Uttarakhand—particularly around educational clusters in Dehradun, Rishikesh, and Roorkee—is a persistent challenge for outstation students. Incoming students frequently face steep broker commissions, misleading photos, and unverified rental terms. Concurrently, graduating seniors struggle to sell functional room essentials such as study tables, desert coolers, reference books, and second-hand two-wheelers, while incoming juniors buy the exact same goods brand new at retail prices. General classifieds like OLX suffer from broker spam and lack room-level vacancy details, while platforms like Airbnb cater exclusively to short-term tourists on daily tariffs.

To solve this practical problem, this project presents StayMart, an integrated student accommodation and campus re-commerce web application tailored for Uttarakhand. The platform is built on a decoupled multi-tier architecture: a Java 17 / Spring Boot 3.3 REST API handling core transactions and role-based access control with stateless JSON Web Tokens (JWT), a normalized MySQL 8.0 relational database with 12 tables, and an asynchronous Python 3.11 / Flask machine learning microservice running a TF-IDF and cosine similarity recommendation pipeline with automated database-driven fallbacks. The frontend is engineered using responsive vanilla HTML5, CSS3, and modern JavaScript inspired by familiar commercial classified interfaces (OLX and Amazon), avoiding heavy client-side framework overhead. Key features include zero-brokerage direct contact with verified property caretakers, peer-to-peer student messaging, room-level vacancy tracking, wishlist management, and an administrative moderation dashboard.

System evaluation confirms sub-50ms database queries under typical loads, reliable recommendation fallbacks when the ML microservice is offline, and clean mobile responsiveness across standard viewports. This report details the software requirements, relational schema, algorithm design, system implementation, and zero-cost cloud deployment guidelines for the platform.

Chapter 1
Introduction and Problem Statement

[[LOC:SEC_1_1]]

1.1 Introduction

Every academic year, thousands of students relocate to higher education hubs across Uttarakhand, including Dehradun, Roorkee, and Rishikesh. Premier institutions such as Graphic Era Hill University (GEHU), UPES, and DIT University attract substantial student enrollments. Outstation scholars face two immediate logistical hurdles: securing safe, affordable accommodation and procuring essential room furnishings within student budgets.

Despite high demand along corridors like Clement Town and Premnagar, the local rental market remains fragmented. Students encounter informal brokers charging high commissions, deceptive photos, and opaque lease terms. Simultaneously, graduating seniors discard functional essentials while incoming juniors purchase identical items brand new at retail rates. To resolve these challenges, this project presents StayMart—a unified student accommodation discovery and campus re-commerce marketplace engineered using Spring Boot 3.3, MySQL 8.0, Flask ML microservices, and a responsive native frontend.

[[LOC:SEC_1_2]]

1.2 Motivation

The core motivation for StayMart arises from persistent challenges in regional campus life:

  1. Brokerage Overhead: Local brokers charge 50%–100% of one month's rent as non-refundable commission, imposing an upfront ₹5,000 to ₹10,000 burden on students.
  2. Unverified Visuals and Amenities: Outstation students frequently encounter inaccurate photos, undisclosed curfews, and concealed utility limitations.
  3. Re-Commerce Value Loss: Graduating seniors sell durable goods for scrap value, while juniors buy identical items at full market cost.
  4. Absence of Contextual Discovery: Existing portals display listings across distant cities without campus proximity filtering or room vacancy awareness.
[[LOC:SEC_1_3]]

1.3 Problem Statement

The problem addressed in this project is formalized as: \begin{quote} “To design and implement a full-stack student accommodation and campus re-commerce web platform for Uttarakhand university corridors, connecting students directly with verified property hosts and student sellers with zero brokerage, room-level vacancy tracking, direct peer messaging, and content-based recommendations.” \end{quote}

Key technical challenges encompass:

  • Dual-Domain Modeling: Unifying accommodation workflows (room configurations, amenities) with product classifieds (categories, condition grading, sell vs. rent).
  • Transactional Integrity: Preventing double-bookings on shared room inventory and ensuring atomic status transitions for single-quantity student goods.
  • Recommendation Dynamics: Delivering campus-relevant suggestions for newly registered students before extensive interaction history exists.
  • Lightweight Interface: Delivering a sub-second, mobile-first interface inspired by OLX and Amazon without heavy client build tooling.
[[LOC:SEC_1_4]]

1.4 Objectives and Project Scope

1.4.1 Primary Engineering Objectives

  1. Architectural Decoupling: Implement a modular 3-tier architecture separating the Presentation Layer (Vanilla ES6), Business Tier (Spring Boot REST), Persistence Tier (MySQL InnoDB), and Intelligence Tier (Flask ML).
  2. Role-Based Security: Enforce stateless authentication with HMAC-SHA256 signed JWTs and role-based access control (ROLE_USER, ROLE_ADMIN).
  3. Content-Based Recommendations: Implement TF-IDF vectorization and cosine similarity scoring with resilient JPA database fallbacks.
  4. Administrative Moderation: Deliver an administrative moderation console to review listings, verify photographs, and govern user accounts.
  5. Peer Messaging and Cloud Hosting: Provide in-app chat for peer communication and containerize services for free-tier cloud deployment.

1.4.2 Project Scope and Regional Focus

The platform targets student belts across Uttarakhand: Dehradun (Clement Town, Premnagar, Rajpur Road), Rishikesh, Haridwar, and Roorkee. It supports six accommodation types (PG, Hostel, Flat, Room, Hotel, Dormitory) and ten consumer goods categories (Electronics, Mobiles, Furniture, Books, Appliances, Vehicles, Sports, Kitchen, Fashion, Others).

2.1 Introduction

Online two-sided marketplaces and accommodation networks have transformed commerce by reducing transaction costs and pairing supply with demand. However, multi-category platforms combining long-term student tenancy with consumer re-commerce in non-metropolitan hill geographies present distinct algorithmic, architectural, and socio-technical challenges that remain unaddressed by generic platforms. This chapter surveys commercial solutions, analyzes recommendation algorithms, evaluates architectural paradigms, and formalizes practical research gaps in Uttarakhand.

[[LOC:SEC_2_2]]

2.2 Survey and Critical Evaluation of Existing Systems

To establish an empirical baseline, we evaluate benchmark platforms across domain focus, transaction models, moderation, and regional adaptability.

2.2.1 OLX and Quikr (General Classifieds)

Horizontal C2C classifieds suffer from lack of domain specialization. In accommodations, OLX fails to capture essential room sharing capacities, floor numbers, meal plans, electricity rules, curfews, or deposit refund policies. Furthermore, absence of pre-publication moderation produces outdated listings and broker spam.

2.2.2 Airbnb and Booking.com (Short-Term Hospitality)

Airbnb provides polished interfaces and calendar bookings, but its financial structure is built for short-term tourism with daily tariffs and 14%–20% service fees. Students in Dehradun require semester leasing without recurring percentage charges. Airbnb also lacks student re-commerce integration.

2.2.3 Flatmates and Nestaway (Shared Rental Networks)

Nestaway operates as a managed real estate company with rigid leases, management premiums, and focus limited to Tier-1 metropolises (Bengaluru, Pune, NCR), maintaining zero operational presence in Uttarakhand educational hubs like Dehradun or Roorkee.

2.2.4 MagicBricks and 99acres (Commercial Real Estate)

These platforms monetize through licensed brokers who purchase lead packs. Students seeking affordable ₹5,000/month rooms near Graphic Era Hill University face aggressive broker calls demanding upfront commissions, defeating direct student-to-owner tenancy.

2.3 Theoretical Analysis of Recommendation Algorithms

Recommender systems predict user preference ratings and surface candidate items from catalogues [resnick1997recommender]. We evaluate Collaborative Filtering against Content-Based and Hybrid approaches to justify StayMart's design.

2.3.1 Collaborative Filtering (CF) and Its Regional Limitations

Collaborative Filtering predicts interest based on historical interaction patterns across users [sarwar2001item]. Pearson Correlation evaluates neighborhood similarity: \begin{equation} \text{sim}(u, v) = \frac{\sum_{i \in I_{uv}} (r_{u, i} - \bar{r}_u)(r_{v, i} - \bar{r}_v)}{\sqrt{\sum_{i \in I_{uv}} (r_{u, i} - \bar{r}_u)^2} \sqrt{\sum_{i \in I_{uv}} (r_{v, i} - \bar{r}_v)^2}} \end{equation} While effective for dense media catalogues [koren2009matrix], CF fails in regional classifieds due to three obstacles: (1) Cold-Start Problem: new room and item listings have zero historical ratings; (2) Matrix Sparsity: localized density typically falls below 0.05%; (3) Inventory Exclusivity: second-hand goods represent single-inventory assets (N=1) that vanish upon purchase.

2.3.2 Content-Based Filtering (CBF) and Vector Space Modeling

Content-Based Filtering evaluates item attribute similarity against user preference profiles [lops2011content]. Each listing is synthesized into an attribute document: \begin{equation} d = \text{Title} \oplus \text{Description} \oplus \text{Category} \oplus \text{City} \oplus \text{Area} \oplus \text{PriceTier} \oplus \text{Amenities} \end{equation} Term Frequency-Inverse Document Frequency (TF-IDF) weights term importance [salton1988term]: \begin{equation} \text{TF}(t, d) = \frac{f_{t, d}}{\sum_{t' \in d} f_{t', d}}, \quad \text{IDF}(t, D) = \log\left(\frac{1 + |D|}{1 + |\{d \in D : t \in d\}|}\right) + 1 \end{equation} \begin{equation} w_{t, d} = \text{TF}(t, d) × \text{IDF}(t, D) \end{equation} With L_2-normalized vectors (\|\vec{u}\|_2 = 1), Cosine Similarity simplifies to the dot product, enabling sub-5ms BLAS computations in scikit-learn [pedregosa2011scikit]: \begin{equation} \text{CosineSim}(\vec{u}, \vec{v}) = \vec{u}^T \vec{v} \end{equation}

2.3.3 Hybrid Behavioral Re-Ranking Framework

To combine content cold-start resilience with user engagement signals, StayMart implements a weighted hybrid re-ranking strategy [burke2002hybrid]. Actions a_k are assigned empirical weights: \text{VIEW} = 1.0, \text{SEARCH} = 2.0, \text{WISHLIST} = 3.0, \text{CONTACT} = 4.0, \text{BOOK/ORDER} = 5.0. The user profile \vec{p}_u incorporates exponential time decay: \begin{equation} \vec{p}_u = \sum_{k=1}^m W(a_k) e^{-\lambda \tau_k} \vec{v}_{i_k} \end{equation} The composite recommendation score combines cosine similarity, campus proximity, and popularity: \begin{equation} S(u, c) = \alpha \cdot \text{CosineSim}(\vec{p}_u, \vec{v}_c) + \beta \cdot \text{LocalityBonus}(u, C_c) + \gamma \cdot \text{PopularityPrior}(c) \end{equation} where \alpha + \beta + \gamma = 1.0, ensuring recommendations strictly align with the student's geographic corridor.

[[LOC:SEC_2_4]]

2.4 Architectural Paradigms: Monolithic vs. Distributed Microservices

In architecting enterprise web applications, the division of responsibilities across compute boundaries is a pivotal design decision [newman2021building, fielding2000architectural].

[[LOC:FIG_2_1]]Figure 2.1: Distributed Microservice Deployment Topology vs. Monolithic Boundaries

A monolithic Spring Boot application executes transactional CRUD and intensive ML vector computations within a single JVM. This causes library limitations (Java lacks native scikit-learn parity) and CPU contention during heavy matrix calculations. StayMart adopts a decoupled topology:

  1. Spring Boot 3.3 Core (Port 8080): Coordinates ACID transactions, JWT authentication, JPA relational entities, and moderation state transitions.
  2. Flask ML Microservice (Port 5000): Operates as an independent service dedicated to TF-IDF transformations, model serialization, and matrix similarity evaluation.
  3. Fault-Tolerant Circuit Fallback: Communication occurs via HTTP REST with 2000ms connect and 3000ms read timeouts. If the ML service is offline, Spring Boot gracefully falls back to database-driven queries matching city and category, eliminating HTTP 500 errors.
[[LOC:SEC_2_5]]

2.5 Modern Frontend Architectures: Vanilla JS vs. Heavy SPAs

Modern single-page application (SPA) frameworks (React, Angular) introduce substantial JavaScript payloads (500KB–1.5MB minified) and build fragility, degrading performance on congested campus cellular networks. StayMart intentionally adopts a Vanilla HTML5, CSS3, and ES6+ JavaScript architecture with zero build steps, delivering sub-45 KB payloads, sub-second rendering, and direct static edge deployment on Vercel or CDN nodes.

[[LOC:SEC_2_6]]

2.6 Identified Practical Gaps and Chapter Summary

Our systematic review reveals four definitive market gaps: (1) absence of dual-inventory accommodation and re-commerce platforms; (2) lack of Uttarakhand hyperlocal campus granularity; (3) cold-start vulnerability in C2C classifieds; and (4) exploitative brokerage fees.

In summary, Content-Based TF-IDF vectorization with behavioral re-ranking resolves the sparsity problem, while a decoupled Spring Boot and Flask microservice architecture paired with a lightweight Vanilla JS frontend provides the optimal balance of transactional integrity, ML compute isolation, and mobile performance. The next chapter details system requirements and architectural modeling.

3.2 Software Requirements Specification (SRS)

3.2.1 User Personas and Actor Hierarchy

StayMart delineates four primary actor classifications interacting within the platform ecosystem:

  1. Guest User: Unauthenticated visitor with read-only access to approved listings, regional filters, and public categories.
  2. Verified Tenant / Buyer: Registered user authenticated via JWT bearer token with privileges to book rooms, order items, save wishlists, and initiate peer chat.
  3. Property Host / Seller: Authenticated listing author managing room inventories, pricing tiers, deposits, condition notes, and order state transitions.
  4. Platform Administrator: Privileged operator (ROLE_ADMIN) governing pre-publication moderation, auditing accounts, and viewing telemetry.

[[LOC:SEC_3_3]]

3.3 High-Level 3-Tier Distributed Architecture

StayMart partitions responsibilities across three decoupled distributed tiers:

  1. Presentation Tier (Client Portal): Vanilla ES6 JavaScript, HTML5, and CSS3 communicating asynchronously over HTTPS via JSON payloads. Stateless JWT tokens are stored in browser storage and transmitted via Authorization: Bearer <JWT> headers.
  2. Business Tier (Spring Boot 3.3 Core): Executing on Eclipse Temurin OpenJDK 17 LTS, this tier implements a Controller-Service-Repository pattern across 16 REST resource controllers, custom JwtAuthenticationFilter, transactional service handlers, and 12 Spring Data JPA repositories.
  3. Persistence and ML Tier: MySQL 8.0 InnoDB provides ACID persistence across 12 normalized tables. A companion Python 3.11 / Flask WSGI service executes TF-IDF vectorization and serves similarity predictions via REST endpoints.

4.1 Introduction

A platform coordinating real-time room bookings, peer re-commerce orders, in-app messaging, and behavioral telemetry requires a robust relational persistence layer. StayMart utilizes MySQL 8.0 with the InnoDB storage engine to guarantee ACID transaction properties, foreign key integrity, row-level locking, and native JSON attribute storage. 4.2 Entity-Relationship (ER) Modeling

Figure 4.1 illustrates the Entity-Relationship diagram for the StayMart database schema.

[[LOC:FIG_4_1]]Figure 4.1: Entity-Relationship (ER) Diagram of the StayMart Relational Database Schema

The schema models key domain associations across the campus ecosystem:

  • Users to Properties (1:N): Hosts author multiple accommodation listings (properties.posted_by).
  • Properties to Rooms (1:N): Properties contain discrete room configurations (rooms.property_id) specifying sharing types and pricing.
  • Locations to Listings (1:N): Geographic nodes (locations.id) standardize campus areas across properties and classifieds.
  • Categories to Products (1:N): Products map into a 10-category re-commerce taxonomy (categories.id).
  • Users to Bookings and Orders (1:N): Students initiate room reservations (bookings.booker_id) and product orders (orders.buyer_id).
  • Users to Peer Chat (N:M via chats): Bilateral communication is recorded linking sender_id and receiver_id with listing context.
  • Users to Telemetry (1:N): Navigation events (views, wishlists, inquiries) are logged in user_behaviors to train recommendations.

4.4 Database Normalization Analysis

To eliminate redundancy and prevent insertion, update, and deletion anomalies, the schema is evaluated against formal normal forms:

  • First Normal Form (1NF): All attributes contain atomic scalar values. Storing serialized photo URLs and amenity lists within MySQL 8.0 native JSON datatypes functions as atomic document storage, avoiding unnecessary join tables while strictly preserving 1NF.
  • Second Normal Form (2NF): All tables utilize single-column surrogate primary keys (id BIGINT AUTO_INCREMENT). Because candidate keys contain no composite attributes, partial key dependencies cannot exist; 2NF is satisfied unconditionally.
  • Third Normal Form (3NF): Transitive dependencies are systematically eliminated. In unnormalized designs, properties storing address attributes directly introduce \text{PropertyID} → \text{Pincode} → \text{City}. Isolating geographic entities into locations ensures all non-key columns depend strictly and non-transitively on the primary key, satisfying 3NF.
  • Boyce-Codd Normal Form (BCNF): For every functional dependency X → Y, X is a superkey (primary key id or unique email). The schema complies with BCNF.
[[LOC:SEC_4_5]]

4.5 Indexing Strategy and Referential Integrity

To guarantee sub-50ms query latency under concurrent load, B-Tree indexes are deployed across critical access paths:

  1. Foreign Key Indexes: Indexed foreign keys on properties(posted_by), rooms(property_id), and orders(product_id) ensure relational joins execute via index range scans rather than full table scans.
  2. Composite Search Indexes: Catalog endpoints frequently filter by approval and availability. Composite indexes on (status, is_available, created_at) enable MySQL to evaluate search predicates directly from the index tree.
  3. Telemetry Stream Indexes: High-throughput event ingestion in user_behaviors is indexed on (user_id, created_at), allowing the recommendation engine to retrieve historical interactions in sub-10ms.

5.3 Security Architecture: Spring Security and Stateless JWT

5.3.1 JWT Authentication Filter Pipeline

Inbound requests are intercepted by JwtAuthenticationFilter before reaching servlet endpoints:

@Component
public class JwtAuthenticationFilter extends OncePerRequestFilter {
    private final JwtTokenProvider tokenProvider;
    private final CustomUserDetailsService userDetailsService;

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain filterChain) throws ServletException, IOException {
        String token = resolveToken(request);
        if (StringUtils.hasText(token) && tokenProvider.validateToken(token)) {
            String email = tokenProvider.getEmailFromToken(token);
            UserDetails userDetails = userDetailsService.loadUserByUsername(email);
            UsernamePasswordAuthenticationToken auth =
                new UsernamePasswordAuthenticationToken(userDetails, null, userDetails.getAuthorities());
            auth.setDetails(new WebAuthenticationDetailsSource().buildDetails(request));
            SecurityContextHolder.getContext().setAuthentication(auth);
        }
        filterChain.doFilter(request, response);
    }
}

Layered security defenses include BCrypt (cost=10) password encryption, Hibernate ORM parameterized queries for SQL injection immunity, and frontend HTML escaping via escapeHtml().

5.5 Fault-Tolerant Fallback Integration in Spring Boot

The Spring Boot backend communicates with Flask via MlServiceClient configured with a 2000ms connection timeout and a 3000ms read timeout. If the ML service is offline or times out, RecommendationService gracefully triggers a JPA database fallback:

@Service
public class RecommendationService {
    private final MlServiceClient mlServiceClient;
    private final PropertyService propertyService;

    public List<PropertyResponse> recommendedProperties(Long userId, String city, int limit) {
        List<Long> ids = mlServiceClient.fetchRecommendedPropertyIds(userId, resolveCity(city), limit);
        List<PropertyResponse> properties = ids.isEmpty() ? List.of() : propertyService.findRecommendedProperties(ids, limit);
        if (properties.isEmpty()) {
            return propertyService.latestApproved(limit); // Resilient JPA fallback
        }
        return properties;
    }
}

8.4 Edge Routing and Local Development Runbook

In production, edge routing is configured directly through vercel.json rewrite rules, forwarding /api/(.*) requests to the cloud backend while serving local frontend assets.

For local development, an automated PowerShell orchestration script (scripts/start-all.ps1) boots MySQL on port 3306, seeds tables, runs Maven compilation, activates Python virtual environments, and starts the frontend proxy:

# Automated single-command startup
pwsh -File scripts/start-all.ps1

# Manual fallback commands
docker run --name staymart-mysql -e MYSQL_ROOT_PASSWORD=root -e MYSQL_DATABASE=staymart -p 3306:3306 -d mysql:8.0
mvn spring-boot:run             # Starts backend at http://localhost:8080
python ml-service/app.py        # Starts ML service at http://localhost:5000
python scripts/serve_frontend.py 5500 # Serves frontend at http://localhost:5500

Chapter 9
Conclusion and Future Scope

[[LOC:SEC_9_1]]

9.1 Summary of Contributions and Completed Milestones

StayMart addresses the logistical and financial challenges encountered by outstation students relocating to higher education hubs in Uttarakhand. By integrating verified accommodation discovery with campus second-hand commerce, the platform connects students directly with verified property hosts and graduating seniors without intermediary brokerage fees.

Key engineering contributions completed in this project include:

  1. Multi-Tier Architecture and Security: A production distributed system combining a Java 17 LTS / Spring Boot 3.3 REST backend, an ACID-compliant MySQL 8.0 database, and stateless HMAC-SHA256 JWT security with role-based access control.
  2. Content-Based Recommendation Engine: A TF-IDF and cosine similarity recommendation microservice built with Python and scikit-learn, backed by resilient JPA database fallbacks ensuring zero user-facing downtime.
  3. Lightweight Classifieds Frontend: A responsive, mobile-first design system built using native HTML5, CSS3 Custom Properties, and modular ES6 JavaScript, delivering sub-45 KB payloads and sub-second rendering.
  4. Governance and Cloud Deployment: Bilateral peer messaging, an administrative moderation portal with Chart.js analytics, and automated free-tier cloud deployment with JVM memory constraints.
[[LOC:SEC_9_2]]

9.2 Societal and Economic Impact in Uttarakhand

The deployment of StayMart provides direct practical advantages for higher education communities across Dehradun, Roorkee, and Rishikesh:

  • Brokerage Elimination: Direct connections around Graphic Era, UPES, and DIT eliminate non-refundable broker fees, saving students ₹5,000 to ₹15,000 per tenancy cycle.
  • Campus Circular Re-Commerce: Graduating seniors sell functional coolers, study desks, and reference books to incoming juniors, reducing waste and living expenses.
[[LOC:SEC_9_3]]

9.3 Lessons Learned During System Development

Key engineering takeaways from developing StayMart include:

  1. Container Memory Guardrails: On free-tier cloud containers (512 MB RAM limit), JVM default memory allocations trigger OOM terminations. Setting -Xmx384m with Serial GC (-XX:+UseSerialGC) ensures container stability.
  2. Defensive Fallback Engineering: Auxiliary ML microservices must be isolated with strict HTTP timeouts (2000ms connect, 3000ms read) and database fallbacks to protect transactional journeys.
[[LOC:SEC_9_4]]

9.4 Limitations of the Current Implementation

Current limitations include manual peer-to-peer UPI settlements without integrated escrow locks, periodic batch model vector updates rather than streaming embeddings, and absence of native GPS-based radius queries.

[[LOC:SEC_9_5]]

9.5 Suggestions for Future Work and Technical Roadmap

Future platform iterations will incorporate: (1) an integrated UPI escrow gateway holding security deposits until physical inspection; (2) geospatial radius filtering (e.g., “within 1 km of GEHU”) via MySQL Spatial; (3) Web Push notifications for immediate chat and booking alerts; and (4) collaborative filtering as platform transaction volumes expand.

[[LOC:SEC_9_6]]

9.6 Concluding Remarks

StayMart demonstrates that practical, student-centric software engineering can effectively solve tangible housing and economic challenges in regional educational corridors. By unifying robust Spring Boot transactions, normalized MySQL schemas, lightweight Python ML vector scoring, and an accessible classifieds user interface, the platform delivers an authentic, zero-cost digital marketplace tailored to higher education life across Uttarakhand.
