[[LOC:ABSTRACT]]
Abstract

Finding safe, affordable rental accommodation near university campuses in Uttarakhand—particularly around educational clusters in Dehradun, Rishikesh, and Roorkee—is a persistent challenge for outstation students. Incoming students frequently face steep broker commissions, misleading photos, and unverified rental terms. Concurrently, graduating seniors struggle to sell functional room essentials such as study tables, desert coolers, reference books, and second-hand two-wheelers, while incoming juniors buy the exact same goods brand new at retail prices. General classifieds like OLX suffer from broker spam and lack room-level vacancy details, while platforms like Airbnb cater exclusively to short-term tourists on daily tariffs.

To solve this practical problem, this project presents StayMart, an integrated student accommodation and campus re-commerce web application tailored for Uttarakhand. The platform is built on a decoupled multi-tier architecture: a Java 17 / Spring Boot 3.3 REST API handling core transactions and role-based access control with stateless JSON Web Tokens (JWT), a normalized MySQL 8.0 relational database with 12 tables, and an asynchronous Python 3.11 / Flask machine learning microservice running a TF-IDF and cosine similarity recommendation pipeline with automated database-driven fallbacks. The frontend is engineered using responsive vanilla HTML5, CSS3, and modern JavaScript inspired by familiar commercial classified interfaces (OLX and Amazon), avoiding heavy client-side framework overhead. Key features include zero-brokerage direct contact with verified property caretakers, peer-to-peer student messaging, room-level vacancy tracking, wishlist management, and an administrative moderation dashboard.

System evaluation confirms sub-50ms database queries under typical loads, reliable recommendation fallbacks when the ML microservice is offline, and clean mobile responsiveness across standard viewports. This report details the software requirements, relational schema, algorithm design, system implementation, and zero-cost cloud deployment guidelines for the platform.

[[LOC:SEC_1_1]]1.1 Introduction

Every academic year, thousands of students from across India relocate to Uttarakhand for higher education. Educational hubs like Dehradun, Roorkee, and Rishikesh host prominent institutions including Graphic Era Hill University (GEHU), Graphic Era University (GEU), UPES, DIT University, Doon University, and IIT Roorkee. For an outstation student moving into these cities for the first time, two immediate practical challenges arise within their first week: finding safe, budget-friendly accommodation (such as a Paying Guest accommodation, student hostel, or shared flat), and acquiring basic daily living essentials—such as a study desk, room cooler, mattress, reference textbooks, or a used two-wheeler—without spending unnecessary money.

Dehradun alone accommodates tens of thousands of outstation students across major campus neighborhoods like Clement Town, Premnagar, Rajpur Road, Ballupur, and Sahastradhara Road. Consequently, the local demand for student housing and affordable second-hand items has grown steadily.

Despite this sustained demand, the local rental and second-hand market in Uttarakhand remains unorganized and frustrating for students. Incoming students often depend on informal local brokers who charge high non-refundable commissions (frequently equal to a full month's rent) simply for sharing contact numbers. Many listings feature misleading photos, unverified amenities, or vague rules regarding security deposit refunds. At the same time, the local market for second-hand student goods is split between cluttered WhatsApp/Telegram groups and general classifieds like OLX, where student listings get buried under dealer ads, spam, and unverified accounts.

To address these everyday challenges, this project presents StayMart—a unified student accommodation discovery and campus re-commerce marketplace web application designed specifically for Uttarakhand. StayMart combines a Java 17 / Spring Boot 3.3 REST backend, a normalized MySQL 8.0 database, an asynchronous Python 3.11 / Flask machine learning microservice for content-based recommendations, and a clean, responsive frontend inspired by established classified platforms like OLX and Amazon.

[[LOC:SEC_1_2]]1.2 Motivation

The driving motivation behind StayMart arises from direct observations and real pain points experienced by university students living around Uttarakhand campus corridors:

  1. High Brokerage Overhead and Financial Drain: Local property brokers typically charge incoming students between 50% and 100% of one month's rent upfront simply for providing a caretaker's phone number. For students managing tight monthly allowances or education loans, paying ₹5,000 to ₹10,000 in non-refundable broker fees creates an immediate financial burden.
  2. Misleading Listings and Neighborhood Geography: Outstation students arriving from other states lack familiarity with Dehradun localities such as Clement Town, Subhash Nagar, Premnagar, and Rajpur Road. Unregulated landlords frequently share misleading photos, conceal room sizes, or fail to mention lack of water storage or power backup during heavy mountain monsoons.
  3. Campus Re-Commerce Waste and Lost Savings: Graduating seniors frequently abandon or sell functional room coolers, study desks, reference textbooks, bicycles, and lab equipment to scrap dealers for nominal sums. Simultaneously, incoming juniors arrive and purchase the exact same items brand new at full retail prices.
  4. Shortcomings of Existing Commercial Platforms: Mainstream platforms fail to address these student-specific needs. Airbnb targets tourists with expensive daily rates; OLX has no room-level vacancy tracking or campus moderation; and platforms like 99acres and MagicBricks are dominated by commercial property brokers.
  5. Lack of Contextual Recommendations: General classifieds display chronological feeds without student-specific filtering. A student searching for a girls' PG near Graphic Era is often shown commercial office spaces or boys' dormitories across distant towns, leading to tedious manual filtering.

[[LOC:SEC_2_1]]2.1 Introduction

The evolution of online two-sided marketplaces and accommodation discovery networks has transformed global commerce over the past two decades. Platforms connecting buyers with sellers, and property hosts with prospective tenants, rely fundamentally on the reduction of transaction costs, the mitigation of information asymmetry, and the efficient pairing of supply and demand. However, the operational dynamics of localized, multi-category platforms—particularly those combining long-term student tenancy with consumer re-commerce in non-metropolitan hill geographies—present distinct algorithmic, architectural, and socio-technical challenges that remain inadequately addressed by generalized commercial products.

This chapter presents a comprehensive literature survey examining:

  1. Existing commercial paradigms in accommodation and re-commerce (e.g., OLX, Quikr, Airbnb, Flatmates, MagicBricks).
  2. Mathematical and algorithmic foundations of modern recommendation engines, contrasting Collaborative Filtering, Content-Based Filtering, and Hybrid formulations.
  3. Architectural patterns in distributed systems, evaluating monolithic enterprise designs against decoupled microservice topologies.
  4. Front-end design systems and performance paradigms, analyzing the trade-offs between heavy single-page application (SPA) frameworks and optimized vanilla JavaScript architectures.
  5. Explicit research and practical gaps identified within the regional context of Uttarakhand.

[[LOC:SEC_2_2]]2.2 Survey and Critical Evaluation of Existing Systems

To establish an empirical baseline, we evaluate several benchmark commercial platforms across key functional dimensions: domain focus, transaction models, moderation mechanisms, recommendation intelligence, and regional adaptability.

2.7.1 OLX and Quikr (General Classifieds)

OLX and Quikr represent traditional horizontal consumer-to-consumer (C2C) classified platforms. They allow public users to publish listings across hundreds of arbitrary categories, ranging from real estate and automobiles to jobs and household appliances.

  • Strengths: Massive brand recognition, high initial inventory volume, and nationwide market reach.
  • Limitations: Horizontal classifieds suffer severely from listing degradation, identity fraud, and lack of domain specialization. In the accommodation domain, OLX fails to capture vital residential parameters such as room sharing capacities (single, double, triple), floor numbers, electricity billing rules, meal inclusion, curfew timings, or student security deposit refund terms. Furthermore, these platforms lack automated listing pre-moderation, resulting in high concentrations of obsolete posts, fraudulent advance-payment scams, and duplicate broker spam.

2.7.2 Airbnb and Booking.com (Short-Term Hospitality)

Airbnb popularized peer-to-peer homestay accommodations, establishing sophisticated UI standards, verified reviews, and integrated calendar booking engines.

  • Strengths: Polished user interface, robust host identity verification, dynamic pricing models, and comprehensive reservation management.
  • Limitations: Airbnb's economic and contractual model is fundamentally engineered for short-term tourism (daily tariffs, steep service fees ranging from 14% to 20%, and mandatory instant card payments). In student hubs like Dehradun, long-term tenants seek monthly or semester-based leasing arrangements without recurring percentage-based platform commissions. Furthermore, Airbnb does not support consumer marketplace re-commerce, requiring students to navigate separate platforms for furnishing their rooms.

2.7.3 Flatmates and Nestaway (Shared Rental Networks)

Specialized co-living and roommate discovery platforms, such as Flatmates (Australia/UK) and Nestaway (India), focus explicitly on urban shared living.

  • Strengths: Detailed roommate preference profiling, gender filtering, and structured deposit management.
  • Limitations: In the Indian market, Nestaway and similar operators function primarily as managed property companies rather than open community marketplaces; they impose rigid operational contracts, charge high management premiums, and concentrate almost exclusively on tier-1 metropolises (Bengaluru, Pune, NCR). They maintain zero infrastructure or operational presence in Uttarakhand's educational cities like Dehradun or Roorkee.

2.7.4 MagicBricks and 99acres (Commercial Real Estate)

These platforms dominate the formal Indian real estate and property sale ecosystem.

  • Strengths: Comprehensive legal verification for commercial land and apartment sales; extensive builder tie-ups.
  • Limitations: Their business models are heavily monetized around licensed real estate agents and brokers who purchase lead packages. A student seeking an inexpensive ₹5,000/month single room near Graphic Era Hill University is subjected to aggressive broker phone calls demanding upfront fees, defeating the objective of direct, transparent student-to-owner tenancy.

[[LOC:SEC_2_3]]2.3 Theoretical Analysis of Recommendation Algorithms

Recommender systems represent a foundational subclass of information filtering algorithms designed to predict user preference ratings and surface relevant candidate items from high-dimensional catalogues [resnick1997recommender]. In this section, we analyze the mathematical and conceptual foundations of Collaborative Filtering, Content-Based Filtering, and Hybrid formulations to justify the selection of StayMart's recommendation architecture.

2.7.5 Collaborative Filtering (CF)

Collaborative Filtering techniques predict a user's interest in a target item by synthesizing historical interaction patterns (ratings, purchases, clicks) across a multitude of users [sarwar2001item]. CF methods are generally subdivided into memory-based (neighborhood) and model-based approaches.

User-Based and Item-Based Collaborative Filtering

In User-Based Collaborative Filtering, the similarity between user u and user v is typically computed using the Pearson Correlation Coefficient:

$$\displaystyle \text{sim}(u, v) = \frac{\sum_{i \in I_{uv}} (r_{u, i} - \bar{r}_u)(r_{v, i} - \bar{r}_v)}{\sqrt{\sum_{i \in I_{uv}} (r_{u, i} - \bar{r}_u)^2} \sqrt{\sum_{i \in I_{uv}} (r_{v, i} - \bar{r}_v)^2}}$$

where I_{uv} represents the set of items rated by both users, r_{u, i} is the rating given by user u to item i, and \bar{r}_u is the mean rating of user u.

In Item-Based Collaborative Filtering, the similarity between items i and j is calculated across all users who have interacted with both items:

$$\displaystyle \text{sim}(i, j) = \frac{\sum_{u \in U_{ij}} (r_{u, i} - \bar{r}_i)(r_{u, j} - \bar{r}_j)}{\sqrt{\sum_{u \in U_{ij}} (r_{u, i} - \bar{r}_i)^2} \sqrt{\sum_{u \in U_{ij}} (r_{u, j} - \bar{r}_j)^2}}$$

Model-Based Matrix Factorization (SVD)

Matrix factorization models map both users and items to a joint latent factor space of dimensionality f [koren2009matrix]. The interaction between user u and item i is estimated through the inner product of their latent vectors:

$$\displaystyle \hat{r}_{ui} = \mu + b_u + b_i + p_u^T q_i$$

where \mu is the overall average rating, b_u is user bias, b_i is item bias, p_u \in \mathbb{R}^f is the user latent vector, and q_i \in \mathbb{R}^f is the item latent vector.

Critical Drawbacks of Collaborative Filtering for Localized Marketplaces

While CF performs exceptionally well in dense, high-volume consumer ecosystems (such as Netflix movie streaming or Amazon retail), it suffers from fatal limitations when applied to regional marketplaces like StayMart:

  1. The Cold-Start Problem: Newly posted rental accommodations or one-of-a-kind pre-owned products have zero initial interactions. In CF, an item with no ratings cannot be represented in the latent factor space and will never be recommended, crippling newly registered student sellers.
  2. Extreme Matrix Sparsity: In a localized marketplace with 500 properties and 2,000 users, the user-item interaction matrix density typically falls below 0.05%. Under such extreme sparsity, neighborhood overlap is virtually non-existent, causing correlation coefficients to collapse.
  3. Unique Asset Exclusivity: Unlike digital media that can be consumed concurrently by millions of users, physical accommodations have finite capacity, and second-hand marketplace products represent single-inventory items (N=1). Once purchased, the item ceases to be available, invalidating long-term collaborative co-occurrence patterns.

2.7.6 Content-Based Filtering (CBF)

Content-Based Filtering recommends items based on the similarity between item attribute representations and a profile of user preferences derived from their past interactions [lops2011content].

The Vector Space Model and TF-IDF Formulation

In StayMart, each accommodation or product listing is transformed into a rich textual document d constructed by concatenating its structural and semantic attributes:

$$\displaystyle d = \text{Title} \oplus \text{Description} \oplus \text{Category} \oplus \text{City} \oplus \text{Area} \oplus \text{PriceTier} \oplus \text{Amenities}$$

To convert textual documents into numerical vectors suitable for geometric distance calculation, we employ Term Frequency-Inverse Document Frequency (TF-IDF) weighting [salton1988term].

1. Term Frequency (TF): Measures the relative frequency of term t within document d:

$$\displaystyle \text{TF}(t, d) = \frac{f_{t, d}}{\sum_{t' \in d} f_{t', d}}$$

where f_{t, d} is the raw count of term t in document d.

2. Inverse Document Frequency (IDF): Down-weights ubiquitous, non-discriminative terms while amplifying rare, informative tokens across the entire corpus D:

$$\displaystyle \text{IDF}(t, D) = \log\left(\frac{1 + |D|}{1 + |\{d \in D : t \in d\}|}\right) + 1$$

where |D| is the total number of documents in the collection, and |\{d \in D : t \in d\}| is the document frequency of term t. The smoothing constant of 1 prevents division-by-zero errors for out-of-vocabulary tokens.

3. Combined TF-IDF Weight:
$$\displaystyle w_{t, d} = \text{TF}(t, d) \times \text{IDF}(t, D)$$

Each document d is subsequently represented as an n-dimensional normalized feature vector \vec{v}_d = [w_{1, d}, w_{2, d}, \dots, w_{n, d}]^T, where n denotes the vocabulary size across unigrams and bigrams.

Cosine Similarity Metric

The semantic similarity between two listing vectors \vec{u} and \vec{v} is evaluated using Cosine Similarity, which measures the cosine of the angle between two non-zero vectors in inner product space:

$$\displaystyle \text{CosineSim}(\vec{u}, \vec{v}) = \frac{\vec{u} \cdot \vec{v}}{\|\vec{u}\|_2 \|\vec{v}\|_2} = \frac{\sum_{i=1}^n u_i v_i}{\sqrt{\sum_{i=1}^n u_i^2} \sqrt{\sum_{i=1}^n v_i^2}}$$

Because vectors are L_2-normalized during vectorization (\|\vec{u}\|_2 = 1), the cosine similarity reduces directly to the dot product:

$$\displaystyle \text{CosineSim}(\vec{u}, \vec{v}) = \vec{u}^T \vec{v}$$

This formulation guarantees computational efficiency, enabling the Flask ML microservice to compute pairwise matrix multiplications in sub-5ms times using vectorized BLAS routines in NumPy and scikit-learn [pedregosa2011scikit].

2.7.7 Hybrid Behavioral Re-Ranking Framework

To combine the cold-start resilience of Content-Based Filtering with the empirical signals of user engagement, StayMart implements a hybrid re-ranking strategy [burke2002hybrid].

Let B_u = \{(i_k, a_k, \tau_k)\}_{k=1}^m represent the behavioral interaction history of user u, where i_k is the interacted item, a_k \in \{\text{VIEW}, \text{SEARCH}, \text{WISHLIST}, \text{CONTACT}, \text{BOOK}, \text{ORDER}\} is the recorded action, and \tau_k is the time elapsed since the action.

Each action is assigned an empirical behavioral significance weight W(a_k):

$$\displaystyle W(a_k) = \begin{cases} 1.0, & a_k = \text{VIEW} \\ 2.0, & a_k = \text{SEARCH} \\ 3.0, & a_k = \text{WISHLIST} \\ 4.0, & a_k = \text{CONTACT} \\ 5.0, & a_k \in \{\text{BOOK}, \text{ORDER}\} \end{cases}$$

The user's dynamic preference vector \vec{p}_u is synthesized as a weighted centroid of their interacted item vectors, adjusted with an exponential time-decay parameter \lambda:

$$\displaystyle \vec{p}_u = \sum_{k=1}^m W(a_k) e^{-\lambda \tau_k} \vec{v}_{i_k}$$

The overall recommendation affinity score S(u, c) for candidate item c located in city C_c is determined by:

$$\displaystyle S(u, c) = \alpha \cdot \text{CosineSim}(\vec{p}_u, \vec{v}_c) + \beta \cdot \text{LocalityBonus}(u, C_c) + \gamma \cdot \text{PopularityPrior}(c)$$

where \alpha, \beta, \gamma are tuning hyper-parameters satisfying \alpha + \beta + \gamma = 1.0. This ensures that recommendations strictly align with the user's geographic corridor while dynamically adapting to their stated interests.

2.7.8 The Monolithic Approach

In a traditional monolithic Spring Boot application, all operations—including transactional user registration, relational CRUD operations, file uploads, and mathematical vector calculations—execute within a single Java Virtual Machine (JVM). While monoliths offer simplicity in initial deployment and zero network serialization overhead, they exhibit substantial drawbacks for data science workloads:

  • Library Ecosystem Limitations: Natural Language Processing, sparse matrix algebra, and scikit-learn models have mature, highly optimized implementations in Python (NumPy, SciPy, scikit-learn), whereas equivalent Java alternatives (Deeplearning4j, Tribuo) lack community parity and impose excessive memory footprints.
  • CPU Resource Contention: Heavy vector operations running on the JVM thread pool can starve Tomcat of worker threads, causing HTTP request latency spikes for standard read/write database transactions.

2.7.9 StayMart's Decoupled Microservice Topology

StayMart implements a hybrid decoupled topology:

  1. Spring Boot 3.3 Core Backend on Java 17 LTS (Port 8080): Manages transactional ACID operations, Spring Security JWT authentication, relational JPA entity mappings, and administrative moderation workflows.
  2. Flask ML Microservice (Port 5000): Operates as an independent, lightweight Python service dedicated to text vectorization, model serialization via joblib, and matrix similarity evaluation.
  3. Fault-Tolerant Resilience: Communication between Spring Boot and Flask occurs via HTTP REST calls managed by MlServiceClient with strict timeouts (2000ms connect, 3000ms read). If the ML microservice is slow or offline, the Spring Boot core backend intercepts the failure and smoothly falls back to database queries matching the requested city and category, preventing 500 errors.

[[LOC:SEC_2_5]]2.5 Modern Frontend Architectures: Vanilla JS vs. Heavy SPAs

Modern web development is heavily dominated by complex Single Page Application (SPA) frameworks, most notably React, Angular, and Vue. While these frameworks provide component abstractions, they introduce significant real-world costs:

  • Massive Bundle Overhead: Typical production React bundles frequently exceed 500KB to 1.5MB of minified JavaScript, resulting in sluggish First Contentful Paint (FCP) and Time to Interactive (TTI) metrics, especially on low-bandwidth mobile networks in hilly regions.
  • Build Tooling Fragility: Reliance on Webpack, Vite, Babel, and nested npm dependency trees introduces supply-chain vulnerabilities, build deprecation cycles, and high hosting complexity.

StayMart intentionally adopts an optimized Vanilla HTML5, CSS3, and Modern JavaScript (ES6+) architecture with zero build steps. Modern ECMAScript features—including async/await, native fetch, template literals, and CSS custom properties (variables)—provide full architectural expressiveness while maintaining negligible page weight (< 45\text{ KB} per page view), near-instantaneous load times, and effortless static hosting on platforms such as Vercel, Netlify, or standard Nginx containers.

[[LOC:SEC_4_4]]4.4 Database Normalization Analysis

To eliminate data redundancy and prevent insertion, update, and deletion anomalies, we evaluate the schema through formal normalization stages.

4.6.8 First Normal Form (1NF)

A relation satisfies 1NF if all attribute domains contain only atomic, indivisible values, and there are no repeating groups.

  • Every column in StayMart—such as price, name, email, and status—contains atomic scalar values.
  • Use of JSON Attributes: Columns like amenities and images in properties and products store JSON arrays. Under MySQL 8.0, the native JSON type functions as an atomic document datatype. Storing image URLs and amenity tags as serialized collections attached to a single listing avoids maintaining separate join tables for static arrays while strictly preserving 1NF.

4.6.9 Second Normal Form (2NF)

A relation is in 2NF if it is in 1NF and every non-prime attribute is fully functionally dependent on the entire primary key (no partial key dependencies).

  • Every table in StayMart uses a single-column surrogate primary key (id BIGINT AUTO_INCREMENT).
  • Because every candidate key consists of exactly one attribute (K = \{\text{id}\}), a partial dependency on a subset of a composite key is impossible. Therefore, all twelve tables satisfy 2NF unconditionally.

4.6.10 Third Normal Form (3NF)

A relation is in 3NF if it is in 2NF and no non-prime attribute is transitively dependent on the primary key. Formally, for every non-trivial functional dependency X → Y, either X is a superkey or Y is a prime attribute.

Practical Case Study: Geographical Normalization (locations) \\ Consider an unnormalized property table containing city, area, and pincode directly:

$$\displaystyle \text{PropertyID} \rightarrow \{\text{Area}, \text{City}, \text{State}, \text{Pincode}\}$$

This design introduces transitive dependencies because:

$$\displaystyle \text{PropertyID} \rightarrow \text{Pincode} \quad \text{and} \quad \text{Pincode} \rightarrow \{\text{City}, \text{State}\}$$

This causes three classic database anomalies:

  1. Redundancy: Every student PG in Clement Town would duplicate the string “Clement Town, Dehradun, Uttarakhand, 248002”.
  2. Update Anomaly: Changing a locality name requires updating hundreds of individual property rows.
  3. Deletion Anomaly: Deleting all listings in a new campus locality would delete the knowledge that the locality exists in the database.

StayMart eliminates this transitive dependency by isolating geographic data into the locations relation. Properties reference location_id as a foreign key. Thus, all non-prime attributes in properties depend directly on the primary key, satisfying 3NF.

4.6.11 Boyce-Codd Normal Form (BCNF)

A relation is in BCNF if for every non-trivial functional dependency X → Y, X is a superkey. In StayMart, all non-trivial functional dependencies originate from primary keys (id) or unique candidate keys (such as users.email), which are verified superkeys. Therefore, the schema satisfies BCNF.

[[LOC:SEC_4_5]]4.5 Indexing Strategy and Referential Integrity

To ensure fast query execution across thousands of student listings, B-Tree indexes are defined on foreign keys and search filter columns:

  1. Foreign Key Indexes: Indexes on properties(posted_by), properties(location_id), products(category_id), bookings(property_id), and orders(product_id) ensure that relational joins execute efficiently via index range scans rather than full table scans.
  2. Search Filter Indexes: The public catalog search frequently filters by approval status and availability. Composite indexes on (status, is_available, created_at) allow MySQL to filter approved listings directly from the index tree.
  3. Telemetry Stream Indexes: The user_behaviors table receives high write volume. An index on (user_id, created_at) allows the recommendation service to retrieve a user's recent interactions in milliseconds.

[[LOC:SEC_5_3]]5.3 Security Architecture: Spring Security and Stateless JWT

5.6.3 JWT Signing and Roles

Upon successful login via POST /api/auth/login, the JwtTokenProvider generates a signed token:

  • Algorithm: HMAC-SHA256 (HS256) using a 256-bit secret key.
  • Token Claims: Subject (email), User ID (id), Role authority (ROLE_USER or ROLE_ADMIN), Issue time (iat), and Expiration (exp, 24 hours).

5.6.4 JWT Authentication Filter

Every inbound HTTP request passes through JwtAuthenticationFilter before reaching the servlet dispatcher:

@Component
public class JwtAuthenticationFilter extends OncePerRequestFilter {

    private final JwtTokenProvider tokenProvider;
    private final CustomUserDetailsService userDetailsService;

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain) throws ServletException, IOException {
        String token = resolveToken(request);
        if (StringUtils.hasText(token) && tokenProvider.validateToken(token)) {
            String email = tokenProvider.getEmailFromToken(token);
            UserDetails userDetails = userDetailsService.loadUserByUsername(email);
            
            UsernamePasswordAuthenticationToken authentication =
                new UsernamePasswordAuthenticationToken(userDetails, null, userDetails.getAuthorities());
            authentication.setDetails(new WebAuthenticationDetailsSource().buildDetails(request));
            
            SecurityContextHolder.getContext().setAuthentication(authentication);
        }
        filterChain.doFilter(request, response);
    }

    private String resolveToken(HttpServletRequest request) {
        String bearer = request.getHeader("Authorization");
        if (StringUtils.hasText(bearer) && bearer.startsWith("Bearer ")) {
            return bearer.substring(7);
        }
        return null;
    }
}

5.6.5 Accurate Security Boundaries

Each security concern is handled at the appropriate architectural layer:

  • Password Encryption: Passwords are encrypted with BCrypt (cost=10) before database persistence.
  • Authentication and RBAC: JWT tokens provide stateless session verification and role enforcement. Standard users have access to personal bookings, chats, and listings, while admin routes require ROLE_ADMIN.
  • SQL Injection Defense: Provided by Spring Data JPA and Hibernate ORM parameterized queries (PreparedStatements), which treat user inputs strictly as literal parameters.
  • XSS Defense: Handled by frontend output sanitization via escapeHtml() in utils.js and input validation annotations in Spring Boot DTOs.

5.6.6 Feature Vectorization and Model Pipeline

For each listing, the service synthesizes a composite text document concatenating title, description, category, campus area, city, amenities, and price tier buckets:

def build_property_document(row):
    tokens = [
        str(row['title']),
        str(row['description']),
        str(row['type']),
        str(row['gender_preference']),
        str(row['area']),
        str(row['city']),
        " ".join(json.loads(row['amenities'])) if row['amenities'] else ""
    ]
    price = float(row['price_per_month'])
    if price < 5000:
        tokens.append("budget_tier_low")
    elif price <= 10000:
        tokens.append("budget_tier_medium")
    else:
        tokens.append("budget_tier_premium")
    return " ".join(tokens)

The composite corpus is transformed into a continuous vector space using TfidfVectorizer with unigrams and bigrams (1, 2), sublinear term frequency scaling, and English stop-word filtering. Cosine similarity calculates relevance scores:

$$\displaystyle \text{Similarity}(\vec{u}, \vec{v}) = \frac{\vec{u} \cdot \vec{v}}{\|\vec{u}\|_2 \|\vec{v}\|_2}$$

The Spring Boot backend interacts with the Flask ML microservice through MlServiceClient. To ensure platform availability when the ML service is offline or starting up, MlServiceClient configures a 2000ms connection timeout and a 3000ms read timeout:

SimpleClientHttpRequestFactory requestFactory = new SimpleClientHttpRequestFactory();

The RecommendationService detects this empty list and immediately falls back to approved database listings:

@Service
public class RecommendationService {

    private final MlServiceClient mlServiceClient;
    private final PropertyService propertyService;
    private final ProductService productService;

    public RecommendationService(MlServiceClient mlServiceClient,
                                 PropertyService propertyService,
                                 ProductService productService) {
        this.mlServiceClient = mlServiceClient;
        this.propertyService = propertyService;
        this.productService = productService;
    }

    public List<PropertyResponse> recommendedProperties(Long userId, String city, int limit) {
        List<Long> ids = mlServiceClient.fetchRecommendedPropertyIds(userId, resolveCity(city), limit);
        List<PropertyResponse> properties = ids.isEmpty()
                ? List.of()
                : propertyService.findRecommendedProperties(ids, limit);
        if (properties.isEmpty()) {
            return propertyService.latestApproved(limit);
        }
        return properties;
    }
}

This design guarantees that even if the Python ML microservice is unavailable, students browsing StayMart continue to receive valid, verified listings without encountering HTTP 500 errors.

[[LOC:SEC_7_4]]7.4 Security Vulnerability and Penetration Testing

Security testing evaluated StayMart against common web application vulnerabilities:

  1. SQL Injection Resilience: All database operations execute through Spring Data JPA and Hibernate ORM utilizing strictly parameterized SQL queries. Injections containing malicious SQL fragments (e.g., ' OR '1'='1) submitted in search queries or login fields are safely escaped as literal strings, eliminating SQL injection vulnerabilities.
  2. Cross-Site Scripting (XSS) Sanitization: Client-side rendering functions in utils.js route dynamic content through the escapeHtml() utility function before DOM insertion. Payloads like <script>alert(1)</script> are transformed into &amp;lt;script&amp;gt;alert(1)&amp;lt;/script&amp;gt;, preventing script execution.
  3. Cryptographic Signature Tampering: A valid JWT token was modified by altering the payload role from "role":"USER" to "role":"ADMIN" while retaining the original signature. The backend JwtTokenProvider failed HMAC verification and immediately rejected the request with HTTP 401 Unauthorized.
  4. Role-Based Access Enforcement: Invoking administrative endpoints (such as GET /api/admin/overview) with a standard user token is intercepted by Spring Security and rejected with HTTP 403 Forbidden.

[[LOC:SEC_7_5]]7.5 Machine Learning Engine and Resilience Fallback Evaluation

The recommendation system combines a content-based TF-IDF model running in Python with a fault-tolerant database fallback in Spring Boot.

7.9.1 Content-Based Matching Logic

The ML microservice uses scikit-learn's TfidfVectorizer with both unigrams and bigrams. When a student browses or searches for listings, the engine constructs a combined feature string from the listing title, category, neighborhood area, and amenity tags. Cosine similarity calculates relevance scores against the user's recent interaction history:

$$\displaystyle \text{Similarity}(A, B) = \frac{A \cdot B}{\|A\| \|B\|}$$

This allows the system to recommend similar PGs near the same university campus or suggest related study equipment.

7.9.2 Cold-Start Handling and Fault-Tolerant Fallback

A practical challenge in student marketplaces is the cold-start scenario—when a newly registered student has no interaction history:

  • User Cold-Start: When no behavioral history exists, the backend provides location-based defaults, prioritizing verified listings near the student's selected campus.
  • Microservice Downtime Fallback: Because the Flask ML microservice may experience cold starts on free cloud containers (such as Render or Koyeb), the Spring Boot MlServiceClient enforces strict timeouts (2000ms connect, 3000ms read). If the ML microservice is slow or offline, the service automatically falls back to native JPA database queries matching the requested city and category. As verified in Test TC-14, the marketplace continues to serve valid listings without returning HTTP 500 errors.

Deployment, Cloud Hosting, and Local Startup Operations

[[LOC:SEC_8_1]]8.1 Introduction

A major challenge when developing full-stack university software projects is hosting costs. Commercial cloud providers often incur substantial monthly expenses for virtual machines, managed databases, and edge gateways. For StayMart, our goal was to architect a production-ready, 100% free-tier cloud deployment topology that enables students, evaluators, and independent developers to deploy and operate the entire platform without incurring server bills.

StayMart is engineered to run seamlessly across two target environments:

  1. Free-Tier Production Cloud Topology: A decoupled cloud setup combining Vercel for static edge CDN hosting and reverse proxying, Render or Koyeb for containerized Spring Boot and Flask microservices, and TiDB Serverless for managed MySQL persistence.
  2. Local Development Environment: A lightweight local setup using Docker for MySQL, native Maven compilation, and a Python virtual environment, orchestrated via a single PowerShell startup script.

[[LOC:SEC_8_2]]8.2 Free-Tier Production Cloud Hosting Topology

The production cloud topology decouples the system into four zero-cost tiers, eliminating single points of failure while respecting free-tier memory and compute constraints.

[[LOC:FIG_8_1]]Figure 8.1: StayMart Production Cloud Hosting Topology Across Free-Tier Providers

The four tiers operate as follows:

  • Tier 1: Static Edge CDN (Vercel): The vanilla HTML5/CSS3/JavaScript frontend is deployed to Vercel's global edge network. Vercel automatically provides HTTPS SSL certificates, global CDN caching, and sub-20ms Time-to-First-Byte (TTFB). Reverse proxy rewrite rules in vercel.json route all /api/* calls directly to the Spring Boot backend, completely avoiding Cross-Origin Resource Sharing (CORS) complexities in production.
  • Tier 2: Core REST Backend Service (Render / Koyeb Free Tier): The Spring Boot 3.3 backend runs in a containerized Linux environment under Java 17 LTS. To ensure reliable execution within the 512 MB RAM limit of free cloud containers, the JVM is configured with strict memory guardrails: -Xmx384m -XX:+UseSerialGC. This prevents the Linux Out-of-Memory (OOM) killer from terminating the container during peak traffic.
  • Tier 3: Machine Learning Microservice (Render / Koyeb Free Tier): The Python 3.11 / Flask recommendation microservice runs as an independent container. It provides a lightweight GET /health endpoint used for health checks and keep-alive monitoring. If the free-tier container experiences a cold start, the Spring Boot backend's 2000ms timeout seamlessly falls back to database-driven recommendations without disrupting the user.
  • Tier 4: Managed Cloud Database (TiDB Serverless / Aiven Free Tier): The relational database is hosted on TiDB Serverless, which provides 5 GB of free storage forever with MySQL 8.0 wire compatibility, automated daily backups, and encrypted connections enforced via TLS/SSL (useSSL=true).

package com.staymart.security;

import io.jsonwebtoken.*;
import io.jsonwebtoken.security.Keys;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Component;

import java.security.Key;
import java.util.Date;

@Component
public class JwtTokenProvider {

    private final Key key;
    private final long validityInMilliseconds;

    public JwtTokenProvider(@Value("${app.jwt.secret}") String secret,
                            @Value("${app.jwt.expiration-ms:86400000}") long validity) {
        this.key = Keys.hmacShaKeyFor(secret.getBytes());
        this.validityInMilliseconds = validity;
    }

    public String generateToken(Long userId, String email, String role) {
        Date now = new Date();
        Date validity = new Date(now.getTime() + this.validityInMilliseconds);

        return Jwts.builder()
                .setSubject(email)
                .claim("userId", userId)
                .claim("role", role)
                .setIssuedAt(now)
                .setExpiration(validity)
                .signWith(key, SignatureAlgorithm.HS256)
                .compact();
    }

    public String getEmailFromToken(String token) {
        return Jwts.parserBuilder().setSigningKey(key).build()
                .parseClaimsJws(token).getBody().getSubject();
    }

    public boolean validateToken(String token) {
        try {
            Jwts.parserBuilder().setSigningKey(key).build().parseClaimsJws(token);
            return true;
        } catch (JwtException | IllegalArgumentException e) {
            return false;
        }
    }
}

def get_similar_property_ids(prop_id, limit=4):
    if not is_ready() or prop_id not in prop_df['id'].values:
        return []
    idx = prop_df.index[prop_df['id'] == prop_id][0]
    sim_scores = cosine_similarity(prop_matrix[idx], prop_matrix).flatten()
    sim_scores[idx] = -1.0 # Exclude self
    top_indices = np.argsort(sim_scores)[::-1][:limit]
    return [int(prop_df.iloc[i]['id']) for i in top_indices if sim_scores[i] > 0]

def get_recommended_property_ids(user_id=None, city=None, limit=6):
    if not is_ready() or len(prop_df) == 0:
        return []
    
    if user_id:
        behaviors = db_connector.get_user_behaviors(user_id, 'PROPERTY')
        if behaviors:
            user_vec = np.zeros(prop_matrix.shape[1])
            for b in behaviors:
                pid = b['item_id']
                weight = float(b['weight'])
                if pid in prop_df['id'].values:
                    p_idx = prop_df.index[prop_df['id'] == pid][0]
                    user_vec += weight * prop_matrix[p_idx].toarray().flatten()
            
            sim_scores = cosine_similarity(user_vec.reshape(1, -1), prop_matrix).flatten()
            if city:
                city_mask = (prop_df['city'].str.lower() == city.lower()).values
                sim_scores = sim_scores * (city_mask * 1.5 + 0.5)
            
            top_indices = np.argsort(sim_scores)[::-1][:limit]
            return [int(prop_df.iloc[i]['id']) for i in top_indices]
            
    # Default city filter
    filtered = prop_df
    if city:
        filtered = prop_df[prop_df['city'].str.lower() == city.lower()]
    return [int(x) for x in filtered['id'].head(limit).tolist()]

User Controller (/api/users)

  • GET /api/users/me: Authenticated endpoint returning current user profile details from the JWT principal.
  • PUT /api/users/me: Updates current user profile (name, phone, city, avatar URL).
  • GET /api/users/\{id\}: Retrieves public user profile (name, joined date, verified badge).

Property and Room Controllers (/api/properties, /api/rooms)

  • GET /api/properties: Public paginated search supporting filters: city, area, type, minPrice, maxPrice, genderPreference, amenities, page, size.
  • GET /api/properties/\{id\}: Retrieves approved property details with attached rooms, amenities, and host information.
  • POST /api/properties: Authenticated endpoint for posting a new property listing (status initialized to PENDING).
  • PUT /api/properties/\{id\}: Updates property details (owner or admin only).
  • DELETE /api/properties/\{id\}: Deletes property listing (owner or admin only).
  • GET /api/properties/pending: Admin-only endpoint listing properties awaiting moderation approval.
  • PATCH /api/properties/\{id\}/approve: Admin endpoint setting status to APPROVED.
  • PATCH /api/properties/\{id\}/reject: Admin endpoint setting status to REJECTED.
  • GET /api/properties/\{id\}/rooms: Lists room configurations (Single, Double, Triple) and vacancies for a property.
  • POST /api/properties/\{id\}/rooms: Adds a room configuration to an owned property.

Marketplace Product Controller (/api/products)

  • GET /api/products: Public search supporting filters: categoryId, city, condition, minPrice, maxPrice, page, size.
  • GET /api/products/\{id\}: Retrieves product details and increments view count.
  • POST /api/products: Creates a student classified listing for sale or rent.
  • PUT /api/products/\{id\}: Updates product details (seller or admin only).
  • DELETE /api/products/\{id\}: Deletes product listing (seller or admin only).
  • GET /api/products/pending: Admin-only endpoint listing items awaiting review.
  • PATCH /api/products/\{id\}/approve: Admin approval endpoint.
  • PATCH /api/products/\{id\}/reject: Admin rejection endpoint.

Booking and Order Controllers (/api/bookings, /api/orders)

  • POST /api/bookings: Submits an accommodation booking request.
  • GET /api/bookings/mine: Lists reservations submitted by current student.
  • GET /api/bookings/incoming: Lists booking requests received by property host.
  • PATCH /api/bookings/\{id\}/status: Updates booking status (CONFIRMED, CANCELLED, COMPLETED).
  • POST /api/orders: Creates a purchase or rental order for a marketplace product.
  • GET /api/orders/mine: Lists orders placed by current student.
  • GET /api/orders/incoming: Lists purchase orders received by product seller.
  • PATCH /api/orders/\{id\}/status: Updates order status.

Peer-to-Peer Chat Controller (/api/chat)

  • GET /api/chat/conversations: Lists active conversation threads with unread counts and last message timestamp.
  • GET /api/chat/messages/\{userId\}: Retrieves message history with a specific user and marks inbound messages as read.
  • POST /api/chat/send: Sends a text message to a recipient.
  • GET /api/chat/unread-count: Returns total unread message count for the current user.

Recommendation and Behavior Controllers (/api/recommendations, /api/behaviors)

  • GET /api/recommendations/user/\{userId\}: Returns personalized top recommendations based on user browsing history.
  • GET /api/recommendations/properties: Returns top-recommended properties for a given city.
  • GET /api/recommendations/properties/\{id\}/similar: Returns semantically similar properties.
  • GET /api/recommendations/trending/properties: Returns listings with highest recent engagement.
  • POST /api/behaviors: Records user telemetry events (views, searches, wishlist additions).

Marketplace Metadata and Statistics Controllers

  • GET /api/locations: Returns list of Uttarakhand cities and student campus clusters.
  • GET /api/categories: Returns product category taxonomy.
  • GET /api/properties/stats: Returns public marketplace statistics (total listings, average rents, verified counts, savings estimates) powering UI counters.

Wishlist and Review Controllers (/api/wishlist, /api/reviews)

  • GET /api/wishlist: Lists saved items for current user.
  • POST /api/wishlist/toggle: Adds or removes an item from personal wishlist.
  • GET /api/wishlist/check: Checks if a specific property or product is wishlisted.
  • GET /api/properties/\{id\}/reviews: Lists reviews and ratings for a property.
  • POST /api/properties/\{id\}/reviews: Submits a rating and review after confirmed stay.
  • POST /api/products/\{id\}/reviews: Submits a review for a purchased product.

Administration Controller (/api/admin)

  • GET /api/admin/overview: Admin KPI metrics (total users, active listings, pending moderation counts).
  • GET /api/admin/users: Lists registered users with role and status management.
  • PATCH /api/admin/users/\{id\}/toggle-status: Enables or suspends a user account.
  • GET /api/admin/stats: Telemetry datasets for Chart.js administrative visualizations.

File Upload Controller (/api/files)

  • POST /api/files/upload: Authenticated endpoint for uploading property and product photographs. Validates MIME types, generates unique filenames, and returns relative asset URLs.
  • GET /uploads/\{filename\}: Serves uploaded photographic assets.
